## Architectural notes for future work

### `emit_to_parent_thread` couples to `ThreadState`

`workflows/emit.py` imports `deerflow.agents.thread_state.ThreadState` and
compiles a noop graph against it (lazily, to avoid an import cycle).
Today emit only targets lead_agent threads, so this is fine. If we add a
second agent type whose threads can host workflows, lift the schema to a
parameter.

### Hints inbox is single-process

`workflows/hints_inbox.py` is a `dict[str, list[str]]` guarded by an
`asyncio.Lock`. Restart-fragile (gateway restart drops queued hints) and
single-process (multi-replica gateway would lose hints across replicas).
Both limitations match the existing constraint that bg workflow tasks
themselves don't survive gateway restart. Swap for a sqlite sidecar or
redis when we need either property.

### `_wait_for_parent_idle` polls 4 Hz

Background runner polls `RunManager.has_inflight(parent_tid)` every 250ms
for up to 60s before each emit. Edge cases:

- If RunManager is unset (langgraph dev mode, unit tests), the wait is a
  no-op — emit fires immediately. Documented in `try_get_default_run_manager`.
- If parent thread is genuinely stuck for longer than 60s, we emit
  anyway and log a warning. Trade-off is documented in
  `background.py`'s docstring.

### `serialize_channel_values` strips internal channels

Three categories filtered: `__pregel_*`, `__interrupt__`, `branch:to:*`.
The `branch:to:*` filter was added 2026-04-28 because emit's noop graph
bleeds them into checkpoint values. If you add a new internal-channel
prefix to LangGraph, update this filter.

### Architecture summary

Three layers, no overlap:
- **Chat 流**: 启动通知(start_workflow ToolMessage) + 终态报告(后端 `_emit_to_parent_thread`,Phase 1 已做)
- **Widget**(workspace nav 底部): 仅当前 thread 进行中 workflow,固定位置
- **LLM 工具**: `get_workflow_progress` 问答通道

### Backend additions

- `workflows/finish_stamp.py` — `stamp_parent_finish(parent_thread_id)` writes `metadata.recent_workflow_finish_at` (ISO, monotonic). Best-effort, swallows errors.
- `workflows/background.py` — calls stamp after `_wait_for_parent_idle`, before each emit, in all three terminal paths (success/empty-report/failure/cancel).
- `app/gateway/routers/threads.py`:
  - `GET /api/threads/{tid}/workflows/active` returns non-terminal children with `progress_fields` projection.
  - `POST /api/threads/{tid}/workflows/{child_id}/cancel` cancels via in-process `_BG_TASKS` (mirrors `cancel_workflow` LLM tool).

### Frontend additions

- `core/workflows/{api,hooks,types,index}.ts` — fetch + mutate + react-query hooks (`useActiveWorkflows`, `useCancelActiveWorkflow`).
- `core/threads/use-thread-viewed.ts` — module-singleton store via `useSyncExternalStore` (matches `core/settings/store.ts`); `hasUnreadFinish` pure helper.
- `components/workspace/active-workflows-panel/`:
  - `selectProgressShape` pure helper (bar / number / running fallback)
  - `ProgressLine`, `WorkflowRow`, `ActiveWorkflowsPanel`
- `workspace-sidebar.tsx` mounts `ActiveWorkflowsPanel` after `RecentChatList`, gated on `isSidebarOpen`.
- `recent-chat-list.tsx` renders red-dot next to threads where `metadata.recent_workflow_finish_at > lastViewedAt[tid]`; effect calls `markViewed` whenever `threadIdFromPath` changes.

### Decisions worth remembering

- **Plan said zustand; we used `useSyncExternalStore`.** Zustand is not in the project; reusing the existing module-singleton + listeners pattern from `core/settings/store.ts` was strictly better than adding a dep.
- **Plan said React-render hook tests with `@testing-library/react`.** Project's vitest config has no jsdom and no testing-library. We tested `api.ts` (fetch + URL/encoding/abort/error) and extracted `selectProgressShape` from `ProgressLine` for branch-logic coverage; the React glue is typecheck-only. Adding jsdom infra was explicitly out of scope.
- **Spec compliance review caught a real bug in the plan.** Plan placed the success-path `stamp_parent_finish` call inside `if report:` — empty-report success would skip the red-dot. Lifted the stamp out; added regression test (`test_run_workflow_background_stamps_finish_on_empty_report`).
- **Code-quality reviewer flagged `cp_tuple is None` was untested.** That's a live production state (child registered in metadata, first checkpoint not yet landed). Added `test_active_endpoint_skips_child_without_checkpoint`.

### Architectural notes for future work

- **Empty-progress case**: when a workflow declares `progress_fields` but the state hasn't materialized those keys yet, `progress` returns `{}` and `ProgressLine` falls through to the "running" italic label. Acceptable.
- **Cache-invalidation polish (B8)** triggers chat-list refetch only on **list shrinkage**. New workflows starting on other threads won't surface red dots until the next `useThreads` natural refresh (stream finish or window focus). This is intentional — red-dots represent **finishes**, not **starts**, so missing the start signal doesn't matter.
- **`recent_workflow_finish_at` in store.metadata**: written from `background.py` via `stamp_parent_finish`, read from `ThreadResponse.metadata` on the chat list. No new field schema; just a known key inside `metadata: dict`.
- **`_BG_TASKS` / `_THREAD_TO_WORKFLOW` are still process-local singletons in `workflows/tools.py`.** Cancel endpoint relies on this. Same constraint as Phase 1: gateway restart drops in-flight cancellation routing along with the workflow tasks themselves.

### What was wrong, what changed

1. **`workflows/emit.py` was using `SystemMessage`.** The frontend's
   `groupMessages()` in `core/messages/utils.ts` only renders
   `human / tool / ai` types — `system` was silently dropped. The Phase 1
   smoke "verified" only that the message landed in the checkpoint, not
   that the user could see it. Switched to `AIMessage`, which also
   matches what message-channel forwarders (Slack/Discord/Feishu) expect
   for assistant-side content. Test:
   `tests/test_workflows_emit.py::test_emit_appends_ai_message_so_frontend_renders_it`.

2. **`useStream` doesn't refetch on out-of-band checkpoint writes.**
   When a workflow finishes after the parent's normal stream has closed,
   the emit's `aupdate_state` writes into the parent checkpoint but
   `useStream` never sees it — the user had to reload the page. Added
   `core/threads/use-thread-reload-tick.ts` (pub/sub keyed by threadId,
   `useSyncExternalStore` like `core/settings/store.ts`).
   `useActiveWorkflows` bumps the tick when active workflow count drops;
   `useThreadStream` listens, fetches fresh state via
   `threads.getState`, and merges any unseen messages into the rendered
   list (deduped by id so the next normal stream cleanly takes over).
   Tests: `tests/unit/core/threads/use-thread-reload-tick.test.ts`.

3. **`/threads/search` was returning workflow child threads.** They live
   on the same checkpointer (so they survive restart and can be queried
   for state) but are not user-facing — they appeared as one
   "Untitled" sidebar row per `start_workflow` call. Source of truth for
   "is this a child" is each parent's
   `metadata.child_workflow_threads`. Collected those ids during search
   and excluded them; defensive parsing for malformed entries. Test:
   `tests/test_threads_search_filters_workflow_children.py`.

### Architectural notes worth remembering

- `useStream`'s "I only refetch on threadId change or stream events"
  contract is permanent. Any future feature that writes into a parent
  checkpoint out of band (workflow emit, scheduled message, channel
  inbound replay …) needs to bump the reload tick or the user won't
  see the message until they reload.
- The reload-tick fetch uses `threads.getState` directly, not
  `messages.getStateHistory` — we only need the latest state and want
  to dedup by `id` rather than diffing checkpoints.
- Filtering child threads from `/threads/search` means the chat list
  is correct, but `GET /threads/{tid}` (and the router child endpoints
  Phase 2 added) still return them. That's intentional — workflow
  tools query child state by id all the time.
